# USB waveform export hardware and driver contract

## Status and hardware gate

USB waveform export is an opt-in bench trial for the JYE Tech DSO138 reference configuration: PCB 109-13800-00C, STM32F103C8T6, and ILI9341. `DSO_USB_STOCK_BENCH_TRIAL` defaults to 0; the ordinary public profile leaves USB off. The authorized stock-board experiment tries the board's factory-standard fixed D+ pull-up, which may be tied to 5 V as shown for R31 in the published schematic. That is a limited bench experiment, not a claim of ST-recommended electrical compliance or production qualification. The existing instrument is normally powered from its 9 V DC input. USB data ground therefore connects the instrument ground to the host PC ground; this interface is **not isolated** and must not be used to make an unsafe mains-referenced measurement safe. Follow the instrument's normal isolated low-voltage bench-use precautions.

The JYE Tech DSO138 user manual, schematic on PDF page 4, publishes R31 as a 1.5 kΩ connection from +5 V VBUS to D+. That is only evidence of the published schematic. It does not prove that R31 is fitted, has that value, or is wired that way on any particular assembled board. The board revision and resistor population must be inspected before connecting a PC or enabling USB firmware.

The STM32F103 medium-density part has an integrated full-speed PHY but **does not have an embedded D+ pull-up**. ST AN4879 Rev. 8 Table 4 (PDF page 4) lists the F102/F103 line with no embedded pull-up; footnote 2 requires the external resistor. RM0008 Chapter 23's F103 USB device register map likewise has no D+ pull-up enable bit. The recommended full-speed D+ pull-up is 1.5 kΩ to 3.0–3.6 V, not 5 V (AN4879 §3.1.1, PDF pages 13–14). If R31 is fitted as published, it is not suitable for the recommended production wiring; the opt-in 5 V stock-board trial is a separate, explicitly limited experiment outside that recommendation. Do not simply remove R31 and assume the MCU replaces it.

### Production wiring recommendation

The following conditions describe the recommended production wiring and remain separate from the opt-in stock-board experiment:

1. D+ and D− connect to PA12 and PA11 respectively, with no conflicting external circuitry.
2. D+ has a 1.5 kΩ ±1% pull-up to a regulated 3.0–3.6 V source. This pull-up is externally switched and remains disconnected until VBUS is detected. Its actual source and switch must be confirmed on the board; do not drive the pull-up from a GPIO or use a 5 V source.
3. VBUS is sensed without exposing an MCU pin to 5 V. PA9 is a candidate input, but is not to be connected directly to VBUS. ST AN4879 §2.6.1 recommends 33 kΩ from VBUS to the GPIO node and 82 kΩ from that node to ground for a 3.0–3.6 V MCU supply. At 5.25 V VBUS and ±1% resistor tolerance, the divider's worst high node is approximately 3.77 V. This is below 3.9 V; verify the exact MCU marking, applicable datasheet absolute-maximum ratings, and board power-off behavior before fitting it. AN4879 warns that a 5 V connection to PA9 while the MCU is unpowered can damage the device and says the voltage must be reduced below 4 V. Use PA9 as ordinary GPIO input with this divider; do not enable the OTG VBUS sensing function on the F103.
4. The D+ pull-up switch has a separately qualified control signal and a hardware default-off state. PA4 is a proposed control GPIO only: repository source and Cube pin configuration do not currently assign it, but its availability on the physical PCB and its routing to a suitable switch have not been confirmed. The circuit must use a qualified external transistor/load switch arrangement so a GPIO controls the switch rather than supplying the pull-up current/voltage. PB15 is BTN_OK and is not available. PA0–PA3 are analog inputs; PA7 is the optional test output; PA13/PA14 remain SWD. Do not take over those pins.
5. With the board on its normal 9 V supply and USB attached, verify that the device does not source power onto host VBUS, that the pull-up is absent without host VBUS, and that no board/PC ground connection creates an unsafe measurement setup. Confirm the final schematic and physical resistor/switch population.

The production recommendation is a switched 1.5 kΩ pull-up to regulated 3.0–3.6 V with VBUS sensing and default-off hardware. The stock-board experiment deliberately does not implement that wiring: it does not access PA4 or PA9 and does not claim the production gate is satisfied. The 5 V pull-up experiment is outside the recommended 3.0–3.6 V pull-up range. The default-off build flag is a software selection only and cannot make an unmodified or unknown board electrically safe.

## MCU and peripheral contract

Use only the STM32F103 USB full-speed **device** peripheral described in ST RM0008 Chapter 23. This is not the STM32F105/F107 OTG peripheral. The USB register base is `0x40005C00`; the dedicated USB packet-memory area is 512 bytes at `0x40006000` (RM0008 §2.2 and §23.5). PA11 is USB_DM and PA12 is USB_DP. Do not add external series resistors to D+/D−; the F103 FS impedance is managed internally (AN4879 §3.1, PDF page 13). ESD protection near the connector is recommended by AN4879 §3.1.1 and §2.3; board-level protection remains to be checked.

The existing clock plan can provide the USB clock without changing acquisition timing: with the existing 72 MHz PLL, set RCC_CFGR.USBPRE to 0 for PLL/1.5 = 48 MHz. RM0008 §7.3.2 (Rev. 21, page 101) says USBPRE must be programmed before enabling the USB APB clock and cannot be changed while that clock is enabled. Preserve SYSCLK 72 MHz, APB1 36 MHz, APB2 72 MHz, ADC clock 12 MHz, and the existing 72 MHz TIM2 timer clock. Do not switch the system clock to make USB work.

### PMA and endpoint allocation

USB PMA is distinct from normal SRAM. It is 512 bytes total, shared with CAN SRAM, and must be statically allocated. The F103 PMA uses 16-bit values through CPU addresses with a factor-of-two spacing relative to logical PMA addresses; do not treat it as a conventional packed byte array. The buffer descriptor table has 8 logical bytes per endpoint (16 bytes in the CPU address view); see RM0008 §23.5.3 and the buffer-table register descriptions. Keep a single explicit allocation table and prove every BTABLE and packet buffer range is in-bounds and non-overlapping before enabling the peripheral.

The current allocation places BTABLE at logical PMA offset `0x00`, EP0 RX/TX at `0x40`/`0x80`, EP1 RX/TX at `0xC0`/`0x100`, and EP2 TX at `0x140`. EP0 uses 64-byte setup/control buffers; EP1 carries 64-byte bulk OUT/IN packets; EP2 has a 16-byte interrupt-IN notification buffer. All ranges lie within the 512-byte logical PMA region.

The implemented CDC-ACM descriptor uses EP0 for control transfers, interface 0 for CDC control with an interrupt-IN notification endpoint on EP2, and interface 1 for CDC data with 64-byte bulk OUT/IN endpoints on EP1. The waveform protocol uses the data endpoints for bounded command frames and waveform reads; see [waveform protocol v1](usb-protocol.md). The controller grants a lease on an immutable held frame and serves bounded chunks from foreground code; USB does not retain pointers into mutable or reused capture memory. EP2 remains NAKed when no notification is required.

### Register access and transfer rules

RM0008 §23.5.2 warns against read-modify-write on `USB_EPnR`. `CTR_RX` and `CTR_TX` are clear-on-write-zero, while `DTOG_RX`, `DTOG_TX`, `STAT_RX`, and `STAT_TX` use toggle-on-write behavior. Build each endpoint-register write deliberately: preserve unrelated pending CTR flags, clear only the serviced flag, and toggle only the requested status/data-toggle bits. Do not use ordinary C bitfield assignment or an unconstrained HAL read-modify-write helper. Apply the same careful write-zero-to-clear discipline to `USB_ISTR` interrupt flags.
The implemented EP0 handles reset, SETUP, and the standard enumeration requests used by the host: `GET_DESCRIPTOR` (including a short initial device-descriptor request and `wLength` truncation), `SET_ADDRESS` (apply the new address only after the status-IN stage completes), `GET_STATUS`, `GET_CONFIGURATION`, and `SET_CONFIGURATION`. Unsupported requests and feature selectors are stalled. Control-transfer DATA toggles and status stages include zero-length status packets. Bulk traffic starts only after configuration. The device does not advertise remote wakeup. RM0008 §23.4 and §23.5 define device states and register behavior.

ST errata ES096 Rev. 15 §2.12 applies to STM32F103x8/B. In particular: account for false wakeup detection in the stated unterminated K-state condition (§2.12.1), avoid relying on ESOF timing being synchronized after resume (§2.12.2), ignore CRC16 bytes stored in PMA because their memory copy can be wrong while hardware CRC checking remains functional (§2.12.3), and keep APB1 above 13 MHz to avoid the documented PMA/count reporting issue (§2.12.4). The configured APB1 clock is 36 MHz.

## Interrupt and foreground budget

The device implementation uses `USB_LP_CAN1_RX0` for the low-priority USB event vector (RM0008 interrupt vector table, §10.1); do not enable CAN on this board. `USB_HP_CAN_TX` is a separate vector and is not required unless the driver deliberately uses the high-priority correct-transfer split. USB interrupts must be lower urgency than acquisition DMA1 Channel 1 so a USB event cannot preempt the sample/DMA deadline. USB may be above foreground work, but must not introduce long interrupt masking or defer acquisition service.

The USB IRQ only masks its NVIC line and publishes a pending bit. It does not process peripheral events. Foreground service handles at most two queued events per pass, including RESET, SETUP and EP0 work, then yields to acquisition/UI servicing. No waveform serialization, formatting, blocking wait, LCD/display operation, large memory copy, storage access, or loop waiting on host progress belongs in the USB IRQ. If the host is not ready or a chunk is unavailable, leave the bulk IN endpoint NAKed and let the host retry. The hardware USB block handles packet timing and handshakes; the firmware must be prepared to return NAK rather than block acquisition. There is no claimed numeric USB IRQ time budget, so the acquisition DMA budget remains the hard priority constraint.

The current first-party F103 driver implements the endpoint and CDC paths directly and does not vendor ST USB middleware. In the opt-in stock trial, startup assumes host VBUS is present; it does not read a VBUS-sense pin. It makes a 20 ms PA12 open-drain low pulse while the PHY is off and its clock is gated, then floats the pin before starting the 48 MHz USB clock. USB initialization runs before panel startup; the blocking delay is confined to boot. The USB IRQ only masks and posts pending events. Foreground service handles at most two events and the protocol layer consumes at most 16 input bytes and one command per step. A nonblocking 1 ms data-endpoint quiesce barrier with EPnR readback writes handles transfer cancellation and halt changes. The CDC notification endpoint remains NAKed unless needed; the implementation does not fabricate constant DCD/DSR notifications.

Foreground USB service is polled from the existing main event loop. Each service step has an explicit small work bound and yields to UI/acquisition servicing. It does not disable interrupts while preparing or copying an entire waveform. A held-frame download was timed once, but this does not establish sustainable throughput or acquisition non-interference; fast capture gaps remain unmeasured.

## Current software result and limits

The R5 opt-in stock-trial image measures 64,456 bytes in a 64,512-byte application region, leaving 56 bytes. Its measured SRAM use is 112 bytes of `.data`, 13,192 bytes of `.bss`, and a 2,048-byte stack reservation; 5,128 bytes remain unallocated and heap use is zero. These build measurements apply to the configured trial profile and are not a hardware compliance claim or a guarantee for other board identities or toolchains. The ordinary source profile keeps USB disabled and source VID/PID defaults remain zero; private test identifiers are not release identifiers.

The R4 restart-failure trace distinguished the requested endpoint state from the register readback: the helper's target was `STAT_RX = VALID` (3), but the verified `EP0R` value was `0` before `ISTR.RESET` became visible. It did not show EP0 reading back as RX VALID. The reset correction treats EP0 `TYPE_MASK == 0` as a transient reset image and defers endpoint status writes until foreground reset service rebuilds EP0 as CONTROL. RM0008 Rev. 21 §23.5.2 documents endpoint-register reset behavior and notes that `CTR_RX`/`CTR_TX` may persist; the guard does not infer reset from raw SE0. Because EP0 BULK also has `TYPE_MASK == 0`, that erroneous image would likewise be deferred until reset service; nonzero wrong types remain detectable. Three automatic software-triggered USB restart checks passed on R5, with valid INFO responses at each first COM check about 4.01–4.05 seconds after the reset command. This is a bounded restart check, not a claim that every startup condition or electrical configuration is qualified.

On the reference board, Windows enumerated the CDC device as COM7 without a driver error. INFO, fragmented-frame responses, identical-request replay, conflicting request-ID rejection and CRC resynchronization passed. Two 1,024-sample RAW downloads of the same held frame produced identical hashes, and a four-second slow-host frame lease passed. A Python host run completed three 1,024-sample Single captures with unique jobs and acquisition epochs. Request acknowledgments took about 1.08 ms; request-to-complete took 83.76–85.39 ms. RAW downloads took 48–62 ms (about 33–42.6 kB/s for sample bytes). Cancel returned `Cancelled`; a 1 ms capture timeout returned `Timeout` and left the job `Cancelled`, with no orphan job.

The R5 host run also completed three 1,024-sample Single captures, with jobs 1–3 and acquisition epochs 786–788. Request acknowledgments took 0.47–1.05 ms. Completion took 160.23 ms for the first request, which included a Busy retry while waiting for readiness, then 80.62 and 81.91 ms. RAW reads took 47.57–53.06 ms (38.60–43.05 kB/s of sample bytes). Cancel returned `Cancelled`; a 1 ms timeout returned `Timeout`, and the final job state was `Cancelled`. There was no controller fault or orphan job. A host `CAPTURE_SINGLE` request requires the scope to be in HOLD with foreground work idle; the host does not take over a running acquisition. These are separate host-requested Single captures, not continuous or gap-free acquisition.

MATLAB R2025b with the canonical client completed INFO and a held-frame read, validated timing/calibration metadata and the time axis, and plotted raw/converted values. The R4 `captureRepeated(3,uint32(3000),0)` run returned three valid 1,024-sample Single captures with epochs 20–22 in 2.944 s. The R5 run returned three 1,024-sample captures with valid 12-bit values, Single mode, increasing time and epochs 793–795 in 2.524 s. MATLAB waited for capture readiness before downloading each frame. The held frame used a 2 µs interval (`72 MHz / 144`) and nominal calibration kind 1, not a measured calibration profile. These separate captures do not establish continuous or gap-free acquisition. Electrical production compliance and acquisition timing under fast repeated operation remain unqualified.
